# Scripts

On the Bash tool's PATH while the plugin is enabled (not in a plain terminal). The skills call them; you rarely need to.

`10x-verify`, `10x-red-proof` and `10x-worktree add` run the project's own gates and setup commands and its test files, so granting them is as strong as granting the agent permission to write files in the repo.

## 10x-worktree

`10x-worktree init|add|list|path|rm <id>|sync-base` — one worktree per ticket.

- `init` first prints where tickets live, `tickets: github` or `tickets: files` (the `tickets` setting; any other value exits 2 before anything is created), then keeps `.10x/` out of git before anything is written there.
- `init <id>` and `add` print `ticket dir: <path>` and `base: <branch> (<ref>)`, the lines the skills resolve `.10x/<id>/` paths and the base from. `init <id>` then prints `plan: approved` (`.10x/<id>/plan.md` is a regular file with a `Status: approved` line), `plan: draft` (any other `plan.md`) or `plan: none`, which `/10x:work`'s Step 0 branches on. Before `plan:` it prints `size: small` when the header of `.10x/<id>/ticket.md` declares it (`Size: small` under the title, or `- size: small` in the header `10x-ticket` writes), the ticket has a criterion under `## Acceptance criteria` or `### Acceptance criteria` above any `## Comments`, no `plan.md` exists (a symlink counts) and the ticket is in no batch (`TENX_BATCH` unset and the id not in `S/batch/tickets`); otherwise no `size:` line. When `add` creates the branch, it records the commit it cut it at in `.10x/<id>/start`.
- Without an id, `init` prints what `/10x:open` drafts from: the drafts directory, each issue form (`form: <file> name: … labels: … title: … required: … fields: …`, values JSON, or `forms: none`), Markdown templates and the banned phrases.
- `rm` deletes a branch still at its recorded start (no commits of its own) and writes no landed record. Otherwise it deletes the branch only if git sees it merged. Once it deletes the branch it writes `.10x/<id>/landed`, one line `landed on <base> at <short sha>`, which `10x-batch init <version>` reads as landed; a symlinked `.10x/<id>` or `landed` is reported and left alone.
- `sync-base` fast-forwards the main checkout's base after a merged PR when it is on the base and git allows the fast-forward (unrelated uncommitted changes are kept).
- Before running git in an existing ticket worktree, `add`, `path`, `rm` and `memory` exit 2 with `refusing to run git in <worktree>: <file> …` when its `.git` file or its admin directory's `commondir` or `gitdir` no longer points at the main checkout, since git would then read another config whose `core.fsmonitor`, filters or hooks run as you; `list` prints such a worktree as a `skipped: <reason>` line instead of its row and exits 1. `rm` cannot remove it (`git worktree remove` would run that config too): inspect it, delete the directory and run `git worktree prune`.

## 10x-land

`10x-land check|rebase|push|merge|wait|squash|pr|comment <id>`, `10x-land issue|ticket|advisory <slug>` — the writes `/10x:close`, `/10x:open` and `/10x:work` need, each built from the ticket id or draft slug alone.

- `check` prints the configured close mode (`mode: <close>`, refusing any value but `pr`, `pr-merge`, `local`), then, before looking for the worktree, `ticket dir: <path>`, `base: <branch> (<ref>)`, `review: <path>` or `review: missing` and `tickets: <github|files>` (refusing any other value), and lists uncommitted changes. In `pr`/`pr-merge` mode on GitHub it prints the branch's PR state (`pr: MERGED <url>` sends `/10x:close` to cleanup), and in `pr`/`pr-merge` mode the repo's PR/MR template in the worktree (`pr template: <path>`, or `none`). Then one `locked test changed: <path>` line, and exit 1, per file `10x-red-proof --lock` locked whose content at HEAD is no longer the locked one.
- Every subcommand that looks up the ticket's worktree exits 2 before running git in it when its `.git` file or admin directory was redirected, as [`10x-worktree`](#10x-worktree) does; so do `10x-test`, `10x-verify`, `10x-red-proof` and `10x-review-packet`.
- `rebase` rebases onto the base (conflicts left for you).
- `push` pushes the ticket branch (lease only if origin has it).
- `merge` squash-merges the open PR/MR into the configured base, pinned to origin's repo and the verified head commit, never a fork's PR/MR, and on GitHub only when the PR's head is the worktree's HEAD, the branch contains `origin/<base>` (exit 4 if it moved) and its checks are green (exit 3 when they are only still running).
- `wait` polls the PR's checks by the same rule until green, failed or 30 minutes.
- `squash` lands the branch on the base as one commit from `.10x/<id>/commit-msg` in `local` mode; for a `gh-<n>` ticket it adds `Closes #<n>` as its own paragraph (before a closing trailer block) unless `commit-msg` has that line, so pushing the base closes the issue.
- `pr` opens the PR/MR from `.10x/<id>/pr-title` + `pr-body.md` or updates only its body, refuses a body that lacks any `##` heading of the template `check` names, and refuses a branch whose PR is already merged.
- `issue` creates an issue from `.10x/drafts/<slug>.md` (existing labels only), then deletes the draft; it refuses `tickets: files` before any `gh` call. With issue forms, it refuses a draft whose `###` field sections are out of the form's field order, before `gh issue create`: `line <n>: "### <label>" is out of the form's field order (it comes before "### <previous label>")`.
- `ticket` (`tickets: files` only) writes `.10x/drafts/<slug>.md` verbatim to `.10x/<slug>/ticket.md` and deletes the draft, with the checks of `issue` for a draft without forms and no `gh` call or `origin`; it refuses `Labels:`, `Type:` and `Form:` header lines, an existing `.10x/<slug>/`, and the slugs `gh-<n>`, `drafts` and `audit` (`audit` is reserved for `.10x/audit/`).
- A draft may carry a `Security: <fingerprint>` header line naming the `.10x/security.md` entry it fixes; it is a header, never part of an issue body, and `ticket` keeps it. `issue` runs `10x-security route` on it first: an entry that routes to `advisory` is refused (`use 10x-land advisory <slug>`), and so is a title or body that names any entry (`10x: draft <slug> contains security entry <fingerprint>`), both before any `gh` call that writes or lists labels.
- A draft may end its header, in either `tickets` mode, with `Size: small` or `Size: normal`; any other value exits 2 with `<draft>: line <n>: invalid Size '<v>' (want small or normal)`. `issue` publishes `Size: small` as the body's first line, a blank line after it (`Size: normal` is published nowhere), and `ticket` keeps it in `ticket.md`. `issue`, `ticket` and `advisory` refuse `Size: small` beside a `Security:` line. `issue` and `ticket` refuse a `Size: small` draft whose body has an inline code span — a leading `./` and a trailing `:<line>` or `:<from>-<to>` dropped — naming a file tracked in the main checkout that matches `security.paths` ([configuration](configuration.md)), naming the `Size:` line and the file.
- `10x-land advisory <slug>` takes the slugs and drafts `ticket` takes, but needs the `Security:` line and an entry that `10x-security route` routes to `advisory` (so it always refuses with `tickets: files`); it refuses `Labels:`, `Type:` and `Form:` lines and a body that names the entry's `path:line`. It opens a draft GitHub security advisory in origin's repo from the draft's title and body and the entry's severity (package ecosystem `other`, named after the repo, vulnerable up to the latest tag; no private fork), writes the draft to `.10x/<slug>/ticket.md` with `Advisory: <ghsa id> <url>` after its `Security:` line, deletes the draft and prints `advisory: <url>` and `ticket: <path>`. When GitHub refuses, it prints `gh`'s error, still writes the ticket without the `Advisory:` line and exits 0. No skill grants it and the grant hook never allows it.
- `comment` posts `.10x/gh-<n>/comment.md` on issue `<n>` of origin's repo, only when the url in `.10x/gh-<n>/ticket.md`'s header is that issue's, then renames it to `comment.posted.md` so it is posted once.
- With `TENX_BATCH` set (every batch worker has it), `issue`, `comment` and `advisory` print `10x: refused inside a batch worker` and exit 2 before checking their arguments or reading anything; the other subcommands run as without it.
- `push`, `merge` and `pr` refuse when origin's push URL names another repo than its fetch URL.
- `push`, `pr`, `comment` and `squash` refuse, before any push, `gh`/`glab` call or commit, text that names an entry of `.10x/security.md` ([10x-security](#10x-security)), whatever its status: `push` checks every commit message in `<base>..<branch>`, `pr` checks `pr-title`, `pr-body.md` and every commit message in `<base>..<branch>`, `comment` checks `comment.md`, `squash` checks `commit-msg`. An entry matches by its fingerprint, its title (any case) or its `path:line` (not preceded by another path character, not followed by another digit). Each hit prints `10x: <file or commit <sha>> contains security entry <fingerprint>` — never the title or location — and the command exits 2.
- With `security.blockClose` set ([configuration](configuration.md)), `check` prints `security: <level>` after `tickets:` (`security: off` without it; exit 2 on a value other than the five severities), and after `clean:` one `security entry open: <fingerprint>` line per confirmed entry found in or seen in the ticket whose status is `new` or `fix-now` and whose severity is at or above the level; any such line exits 1. Without the key it never reads `security.md`.

## 10x-verify

`10x-verify <id>` runs every gate once; fails if the tree moved during the run.

## 10x-red-proof

`10x-red-proof <id>` runs the changed tests at HEAD, then reverts the implementation and checks they go red (jest, vitest, `node --test`, or the `redProof` command of any other stack); a test that fails at HEAD exits 2.

`10x-red-proof <id> --lock` is `/10x:work`'s tests half. It exits 2, naming the file, when the branch changes a file that is neither a test nor a test helper (`package.json` and lockfiles included), leaves out a test file `## Tests` names, has a test file that passes at HEAD, has a test the runner reports skipped or todo, or adds an unconditional skip (`.skip(`, `xit(`, `it.todo(`, `{ skip: true }`). Otherwise it records the lock in the worktree's git directory, `10x-lock`: the commit, and the blob of every file the branch changed, test helpers included. It refuses a second lock: a change to a locked file goes through a relock. A ticket `10x-worktree init` reports as `size: small` needs no `## Tests` table; any other ticket whose `## Tests` names no test file exits 2 (`names no test file`), and a branch with no changed test file exits 2 for either (`write the failing tests first`).

With a lock, `10x-red-proof <id>` exits 2 naming each locked file whose blob at HEAD differs from the lock, unless the relocks not yet taken in `.10x/<id>/relock.md` account for it. They are checked in file order, and each must be an entry with a `reason`, an `approved` ruling and a `commit` that is an ancestor of HEAD and changes only locked files, whose parent holds the locked files as the lock before it left them; HEAD must hold them as the last one left them. Several relocks may be pending at once, and one relock may cover several locked files. When every test file then goes red, it moves the lock through each relock commit in order (`relocked at <sha>`). A test file the lock does not hold, changed or new, is free. With TDD on, it refuses to run without a lock while `## Tests` names a test file; with `"tdd": false` ([configuration](configuration.md)) it runs without a lock, and `--lock` is refused.

A changed test file that stays green may be accepted, only on your explicit go, never by the implementer alone: an entry of `accepted-green.md` — `## Accepted <n>` with `- file: <path>`, `- blob: <its blob at HEAD>` and `- reason: <why>` lines — makes `10x-red-proof <id>` print `accepted <file>` and the reason instead of `GREEN`, and exit 0 when no other file stayed green; approved relocks are then applied as in an all-red run. The last entry for a file wins, and only while the file's blob at HEAD is the recorded one: an edited file is `GREEN` again. An entry without a file, a valid blob (40 or 64 lowercase hex) or a reason exits 2 before the tree is touched, naming `accepted entry <n> (<file>)`. The record is `.10x/<id>/accepted-green.md`, which `/10x:work` writes in an interactive session on your go; when `TENX_BATCH` is set or the ticket is in the current batch's `S/batch/tickets`, it is only `S/batch/<id>/accepted-green.md`, which [`10x-batch accept-green`](#10x-batch) writes, so a worker's own `.10x/<id>/accepted-green.md` does not count. Like `TENX_BATCH`, this is a layer, not a boundary: the state dir is found from `XDG_STATE_HOME`, which a worker controls, and red-proof's verdict is the worker's own. `--lock` ignores acceptances.

## 10x-test

`10x-test <id> [test file…]` runs test files in the ticket's worktree with the runner `10x-red-proof` detects, without touching the tree: the files given (relative to the worktree root), or else every test file the branch changed — committed, uncommitted or untracked. It prints the runner's output, then `pass <file>` or `FAIL <file>` per file; exit 1 when a test fails, 2 when it cannot run (no test file, a path outside the worktree, an unsupported stack, or `10x-verify` or `10x-red-proof` holding the ticket's tree). `/10x:work` runs tests only through it, so a `/10x:batch` worker needs no settings rule for the project's test runner.

## 10x-plan-check

`10x-plan-check <id>` refuses `.10x/<id>/plan.md`, naming every line at fault, when:

- a criterion has no `## Tests` row, or the Tests table is missing or has another header;
- a phrase from `references/banned-phrases.txt` appears outside code;
- `## Readers` is empty or an entry has no hit line;
- a `## Tool behaviour relied on` claim has no `$` command block with output;
- `## Overlap` is empty;
- no line outside code is exactly `# Appendix` (`no "# Appendix" line`), or a later one repeats it (`a second "# Appendix" line`); the first one counts;
- a `##` section above `# Appendix` is not one the user is shown — `Goal`, `Acceptance criteria`, `Files`, `Risks and assumptions`, any case, none required, any order — (`"## <name>" belongs below "# Appendix"`), or one of those four is below it (`belongs above`);
- more than 40 lines lie above `# Appendix`, trailing blank lines dropped (`user-facing part is <n> lines, over 40`, on the marker's line);
- and, ending in `cold read required: <n> files — …`, when `## Files` has more than three top-level bullets and `.10x/<id>/cold-read.md` is missing, blank or not a regular file.

On a pass it prints `plan ok: <path>`, then `user-facing: lines 1-<n>`: the lines above `# Appendix`, which `/10x:work` shows the user.

## 10x-review-packet

`10x-review-packet <id> [--fixes]` runs `preReviewGates` first (a failure exits 1, no packet), then builds the reviewer's starting material: diff, changed files, conventions, last verify result, and `## Plan checks` — each `## Tests` case not among its test file's added lines on the branch, and each `(gone)` Readers term still in the tree.

- It adds `security review: required` with the reasons when the diff touches a script a skill grants in `allowed-tools`, a skill's or agent's frontmatter, `hooks/hooks.json`, a script it registers, or a file such a script or hook loads (one level, by a static `source` or relative `require`), and, after those reasons, one `<file> matches security.paths` per changed file matching a glob of `security.paths` (`--no-renames`, nothing excluded). `security.paths` is read from the main checkout's `.claude/10x.json` only, so a branch cannot drop its own entry; a value that is not an array of non-empty strings, none starting with `:`, exits 2.
- For a small ticket (as `10x-worktree init` reports it) it prints `- size: small` after the `security review` line and lists `ticket.md` as what the ticket asks for; when the diff requires a security review, the line is `- size: small, escalated to normal (security review: required)`. A ticket that is not small gets no `size` line. `--fixes` prints it for its own diff.
- `--fixes` covers only the commits since the last review, with its findings (the plan checks still read the whole branch).
- Before the gates, it exits 2 naming each locked file that changed since the lock: run `10x-red-proof <id>`, where a relock is accepted.
- `## Relocks` lists every entry of `.10x/<id>/relock.md`: its heading; for each relock red-proof accepted, the diff of the locked files between the two locks, in a fence longer than any backtick run in it; then its reason and ruling, labelled as written by the implementer and not verified.
- `## Accepted GREEN` follows it: each acceptance red-proof would use — the last entry for its file in the record red-proof reads, its file changed on the branch and its blob the file's at HEAD — as `` - `<file>` at `<blob>` — <reason> ``, under `Recorded by the user, not by the implementer:` (the state-dir record) or `Written to .10x/<id>/accepted-green.md on the user's go:`; `none` when there is none. A malformed entry exits 2 before the gates, with no `review-head` written.

## 10x-batch

The mechanics of `/10x:batch`. Refusals print `10x-batch: <why>` on stderr with exit 2. With `TENX_BATCH` set — every worker has `TENX_BATCH=1` — `init`, `run`, `drop`, `approve`, `accept-green`, `checked` and `loop` print `10x-batch: refused inside a batch worker` before reading or writing anything; `status` still runs.

- State directory `S`: the records `10x-batch` decides from live outside every path a worker may write, in `S` = `$XDG_STATE_HOME` (when set and absolute, else `$HOME/.local/state`)`/10x/<h>`, where `<h>` is the first 16 hex characters of the sha256 of the real path of the repository's git common directory, so every worktree of one repository shares it. `S`, `S/batch` and `S/batch/<id>` are created `0700`, and a symlink at any of them is refused. `init`, `run`, `drop`, `approve`, `accept-green` and `loop` refuse with `10x-batch: state dir <S> is inside <path>` (exit 2) when `S` is, or lies inside, the main checkout, a worktree, a `filesystem.allowWrite` path of the worker settings below, or a `sandbox.filesystem.allowWrite` entry of `<main checkout>/.claude/settings.json` or `settings.local.json` or `~/.claude/settings.json` or `settings.local.json` and, when `CLAUDE_CONFIG_DIR` is set (even empty), the same two files in that directory resolved against the main checkout, where Claude Code reads user settings then; `status` runs without the check. `10x-batch` never reads `<git common dir>/10x-batch/`: a plan approved before this layout needs a new approval.
- `10x-batch init [--auto] <arg>... [--search "<query>"]` resolves every argument to a ticket (`gh-<n>`, `<n>`, `#<n>`, an issue URL of origin's repo, an existing id) before writing anything, then writes `S/batch/mode` (`auto` for `init --auto`, else `default`), `S/batch/tickets` and the board `.10x/_batch/board.md`, whose `mode: <mode>` line follows its heading. A batch with an unsettled ticket is not replaced; a settled one (one with `S/batch/tickets`) is moved to `.10x/_batch.<timestamp>/` and `S/batch.<timestamp>/` together, under one stamp free in both. With `.10x/_batch/tickets` but no `S/batch/tickets`, `init` exits 2 (`.10x/_batch is a batch from before the state dir; finish it with the previous version, or move it away`). Files under `.10x/_batch/` that moved to `S` are ignored.
- Batches take only your own issues: `init` checks each `gh-<n>` it resolves, `ticket.md` already there or not, against the `gh` login, then writes its `ticket.md` with `10x-ticket` again even when one exists, so a file an earlier batch's worker edited is replaced (an existing one is checked first, and a stranger's is left untouched). The check uses the `gh` login (`gh api user --jq .login`, compared case-insensitively) and refuses the whole batch with `not your issue: gh-<n> (author <login>)` (`author unknown` with no author) or `cannot check the author of gh-<n>: <why>`. A ticket file is never checked, so a batch of them calls no `gh`. `run` repeats the check for a `gh-<n>` before any reply or worker.
- An argument that resolves to no ticket, is not a number and names a version of `.10x/roadmap.md` stands for the ticket ids in that version's row. A row with no id exits 2 (`version <v> has no ticket ids: run /10x:roadmap tickets <v>`); an id with `.10x/<id>/landed`, whatever its ticket source, and a `gh-<n>` whose issue is closed are left out and count as landed — unless the id is also named directly, which batches it again. The versions are recorded in `S/batch/versions` (the landed and closed ids in `S/batch/versions.closed`), and once every id of a version is `landed` (`pr-open` does not count) and none has a pending hand check (a version with one keeps its `State`), `status` or `init` rewrites only that row's `State` cell to `Done <YYYY-MM-DD>` (local date, never moved once written) and prints `roadmap: <version> Done <date>`.
- `10x-batch run <id> <plan|reply|implement|close>` runs one worker turn in the foreground: `claude -p` (or `$TENX_BATCH_CLAUDE`) with `--session-id`, or `--resume` for `reply`, which sends `.10x/_batch/<id>/reply.md`. Every worker starts with `--permission-mode auto`, no `--allowedTools`, `--settings <json>` right after `--verbose` (below), and `--disallowedTools` for each command the [grant](hooks.md#grant) hook always asks for (`Bash(<cmd>:*)` and `Bash(<cmd> *)`) and `Edit(//<S>/**)` plus `Edit` on the settings files `<main checkout>/.claude/settings.json`, `settings.local.json`, `~/.claude/settings.json` and `~/.claude/settings.local.json` and, when `CLAUDE_CONFIG_DIR` is set (even empty), the same two files in that directory resolved against the main checkout, where Claude Code reads user settings then, each also at its real path and, when it is a symlink, where it points, which a worker's Write and Edit tools could otherwise use to reach the records or widen the sandbox, and `Edit` on the files a process outside the sandbox later runs: `<git common dir>/**` (the repository's real git common dir: config, hooks, `info/attributes`, every worktree's config), `<worktree dir>/*/.git`, `<main checkout>/.envrc`, `<main checkout>/.claude/10x.json` (its `setup` runs outside the sandbox, and its `worktreeDir` and `close` decide a later worker's denies; the ticket's own worktree copy stays writable), `$ZDOTDIR/.zshrc`, `.zshenv`, `.zprofile`, `.zlogin`, `.zlogout` and the compiled `.zwc` of each (`~` when `ZDOTDIR` is unset or relative) and `~/.zshenv`, `~/.zshenv.zwc`, `~/.bashrc`, `~/.bash_profile`, `~/.bash_login`, `~/.bash_logout`, `~/.profile`, `~/.gitconfig`, `~/.config/git/**` (and `$XDG_CONFIG_HOME/git/**` when it is absolute), `~/.ssh/config`, `~/Library/LaunchAgents/**`, `~/.config/systemd/user/**`, `~/.config/autostart/**`, the plugin's root, `~/.claude.json`, `~/.claude/plugins/**` and `~/.claude/hooks/**` (and, when `CLAUDE_CONFIG_DIR` is set, its `.claude.json`, `plugins/**` and `hooks/**`), every absolute `PATH` entry and `$PNPM_HOME` (when absolute) as `<dir>/**`, whose commands your shell runs, and the caches whose contents run later, `~/.npm/_npx/**`, `~/Library/Caches/pnpm/dlx/**`, `~/.cache/node/corepack/**` (and `$COREPACK_HOME/**` when it is absolute), each as a real path and, when it is a symlink, its target too. The sandbox's `denyWrite` carries the same files for Bash, directories without `/**`, plus the settings files above (under an empty or relative `CLAUDE_CONFIG_DIR` they lie in the main checkout, the worker's cwd, which Bash can write), except the git common dir: it is narrowed to the files git runs code from (`config`, `config.worktree`, `hooks`, `info/attributes`), to `commondir`, which redirects git to another config, and to the admin dir and `.git` file of every worktree registered when the run starts, except the ticket's own `<worktree dir>/<id>`, so the worker's own commits and `10x-worktree add` and `rm` keep working; a plan session's worker gets `TENX_BATCH_PLAN_DIR`, so the [plan boundary](hooks.md#plan-boundary) hook keeps its file writes under `.10x/<id>/`. When the worker's stream-json `init` event reports another mode — Claude Code starts a session in its default mode, without an error, when auto mode is unavailable — `10x-batch` stops it and falls back to the turn again in the mode used before auto mode: `default` with `Edit(.10x/<id>/**)` for a plan session, `acceptEdits` for implementation and close; the rerun is a new run (a new session, or the same one for a reply), and its `<nn>-fallback` file names the mode, shown on the board as `auto mode unavailable: ran in <mode>`. It records `runs.tsv` under `S/batch/<id>/` and the stream-json log, the permission denials and `turn.md` (every assistant text block of the run) under `.10x/_batch/<id>/`, and refuses what `status` would not list, and a reply starting with `/`, which the worker would take as a typed command. It also refuses, with exit 2 and no worker started, a `PATH` entry or `PNPM_HOME` that is or contains the main checkout or an `allowWrite` path (`10x-batch: PATH entry <p> contains <path>`, or `10x-batch: PNPM_HOME <p> contains <path>`): denying it would deny what the worker must write, and leaving it would let the worker plant a command your shell runs; `loop` reports such a ticket as `failed` with that line.
- The `--settings` of every worker run (plan, reply, implement, close and the fallback run) is the JSON of `{"sandbox":{"enabled":true,"allowUnsandboxedCommands":false,"failIfUnavailable":true,"enableWeakerNetworkIsolation":true,"filesystem":{"allowWrite":[<tmp>,"~/.npm","~/Library/Caches","~/.cache","~/Library/Developer","/dev/stdout","/dev/fd"],"denyWrite":[…]},"network":{"allowedDomains":["*"],"allowLocalBinding":true}}}`, with `<tmp>` the conductor's `os.tmpdir()`, `~` its home and `denyWrite` the ticket's list from the entry above, built when the run starts. [The loop](loop.md#the-batch-sandbox) says why each is there. Claude Code keeps only the last `--settings` flag, so a `TENX_BATCH_CLAUDE` wrapper that needs settings of its own must merge them into the flag it is given, not pass a second one.
- When the sandbox is unavailable the worker exits 1 at startup with a `result` event whose `startup_failure_reason` is `sandbox_required_unavailable`. That run is never retried, in any mode, and gets no auto-mode fallback; the run writes `<nn>-sandbox` (`unavailable`), the board shows the ticket `failed` with the evidence `sandbox unavailable` instead of `run <nn> (<kind>) exited 1`, and `loop` reports it as a `failed` item.
- `10x-batch status` rewrites and prints the board, then the actions allowed now: `plan <id>`, `implement <id>`, `close <id>`, `answer <id>` (` approvable` when a passing draft can be approved) and `done`. After `## Needs the human`, the board has a `## Hand checks pending` section with one line per pending hand check, `- <version> — <id> AC<n>: <text>`, for every `landed` ticket of the batch and every id in `S/batch/versions.closed`: a criterion the plan's `## Tests` declares a hand check (`—` as test file, a case starting with `hand check:`) whose last line in `.10x/<id>/evidence.md` is `hand-check: <text>`, `<text>` flattened to one line. A ticket's version is the first name in `S/batch/versions` whose roadmap row lists its id; a ticket in none, or every ticket when there is no `versions` file, no roadmap or one that fails its check, is listed under `(no version)`. Lines follow `S/batch/versions` and each row's ids, then the tickets in no version in board order, and within a ticket the plan's criterion order. The section is absent when nothing is pending, and it changes no action: a batch is `done` with hand checks pending.
- `10x-batch drop <id>` writes `S/batch/<id>/dropped`, stops the ticket's running worker and never schedules it again.
- `10x-batch approve <id>...` records your approval of each id's draft plan that passes `10x-plan-check` — one record per id, the hash of its `plan.md` with its Status line blanked, in `S/<id>.approved`, out of reach of every worker's file tools and its sandboxed Bash — and writes each id's approve reply, printing `approved:`, `plan:` and `reply:` per id. A repeated id counts once. When any id is not in the batch or not waiting with an approvable draft, it prints one `10x-batch:` line per such id and exits 2, writing nothing for any id. No skill grants it: each approval asks your permission. `init` deletes the records (`S/<id>.approved`, `S/<id>.commenters`) of the tickets it takes in, so a ticket batched again needs a new approval. A plan session's ticket is `approved` only when `plan.md` says so and still matches that record; a plan that approves itself, or changes after your approval, is `failed`.
- `10x-batch accept-green <id> <file> "<reason>"` records your acceptance of a test file that stays `GREEN` in [`10x-red-proof`](#10x-red-proof): it appends `## Accepted <n>` with the file, its blob at the ticket worktree's HEAD and the reason (newlines flattened to spaces) to `S/batch/<id>/accepted-green.md`, and prints `accepted: <id> <file> blob <12 hex>`. It exits 2 when the ticket is not in the batch or is dropped, has no worktree or one whose `.git` file or admin directory was redirected (as [`10x-worktree`](#10x-worktree) refuses), the reason is empty, or `<file>` is not a test file (`redProof.tests` when `redProof.command` is set, else red-proof's `*.test|spec.*` pattern) the branch adds or modifies against its merge base. No skill grants it: each acceptance asks your permission, and it writes no `reply.md`. `init` archives `S/batch/`, so acceptances do not carry over to a new batch.
- `10x-batch checked <id> AC<n> "<what you saw>"` records a hand check you ran: it appends `- AC<n> — met: hand check by the user on <YYYY-MM-DD>: <what you saw>` (newlines flattened) to `.10x/<id>/evidence.md` and prints `checked: <id> AC<n>`, for a ticket in the current batch or not. It exits 2 (`checked <id> refused: <why>`), writing nothing, when the words are empty, the criterion's last state is not `hand-check:`, the plan does not declare it a hand check, or `.10x/<id>`, its `plan.md` or its `evidence.md` is missing or a symlink; with other than three arguments it prints the usage. It writes no state-dir record, so it runs no state-dir check. No skill grants it: each record asks your permission. The next `status` or `init` marks a version `Done` once its last pending hand check is recorded.
- `10x-batch loop` (no arguments) drives the batch until a human is needed. Each pass writes the board and starts, as a detached `10x-batch run` whose stderr goes to `.10x/_batch/<id>/run.err`, every `plan`, `implement` and `close` action and a reply for each `answer` whose `reply.md` exists, in both modes. In `auto` mode, for a waiting plan session with neither `.10x/<id>/comment.md` nor `product-questions.md`: an approvable draft gets the same record and reply as `approve` plus `S/batch/<id>/auto-approved` (its hash), shown first in the ticket's evidence as `auto-approved (sha256 <12 hex>)`, unless it is a `gh-<n>` whose comments — on the issue now (`gh issue view <n> --json author,comments`) or under `## Comments` in its `ticket.md` as `init` saw it, recorded in `S/gh-<n>.commenters` (no record holds the plan) — include one by anyone but the issue's author, compared case-insensitively, or cannot be listed — that ticket is held for the rest of the run and becomes an `approve` item; any other draft gets a fixed reply telling the worker to answer technical questions itself under `## Auto decisions` and list product questions in `product-questions.md`, at most 3 times. Between passes it waits for one of its runs to end, or 10 seconds. A ticket whose run is refused as `not your issue` or `cannot check the author` is not started again and becomes a `failed` item with that line; the other tickets go on. Once nothing runs it prints one line, `{"items":[…]}`, one item per ticket in board order — `{"id","need","evidence"}` with `need` `failed`, `answer`, `approve` or `denied` (a latest run with denials on a ticket not landed, `pr-open` or dropped) — or `[{"need":"done"}]` when every ticket is settled, and exits 0. SIGTERM stops `loop` alone; its runs go on, and the next `loop` waits for them.

`batch.parallel` ([configuration](configuration.md)) caps the implementation workers.

## 10x-roadmap

`10x-roadmap show [<version>] | check | apply | link <version> <item n> <id>` — the one reader and writer of `.10x/roadmap.md` for `/10x:roadmap` (and the parser `10x-batch` shares, `scripts/roadmap.js`). Refusals print `10x-roadmap: <why>` with exit 2.

- The file has a table whose header row is `| Version | Contents | Why this order | State |`, then `## Not yet assigned`, `## Later` and `## Decided against`, each once. A `Version` matches `^[A-Za-z0-9][A-Za-z0-9._-]*$`, is not all digits and is unique; `Contents` holds items separated by `; `, an item's ticket id being its last code span (`gh-<n>`, or an id with `.10x/<id>/ticket.md`); `Why this order` is never empty; a `## Decided against` entry gives a reason after ` — `.
- `show` prints `<version> — <state>`, `  <n>. <item>` per item, then `next: <version|none>` (the first version not `Done <YYYY-MM-DD>`), then the pre-release prompt: `audit: /10x:audit <tag>..HEAD` when the main checkout's HEAD is ahead of its latest tag, `audit: no tag — a diff-scope audit needs a previous release` without a tag, and no `audit:` line when HEAD is the tag; with a version, only that version and no `next:` or `audit:` line. Without a roadmap it prints `no roadmap: .10x/roadmap.md` and exits 0. It never writes.
- `check` validates `.10x/roadmap.draft.md`: exit 1 with one `<file>:<line>: <why>` per fault, else one `not kept: <line>` per row or section entry of `roadmap.md` that the draft no longer has byte for byte (a row anywhere in the table, an entry in its own section), then one `new id: <version> <id>` per ticket id a draft row has and the same version's row in `roadmap.md` does not.
- `apply` runs `check`, writes nothing on a fault, else renames the draft to `.10x/roadmap.md` and prints `roadmap: <path>` and the `not kept:` and `new id:` lines.
- `link` appends `` `<id>` `` to an item; it refuses an item that already has an id, and an id that is neither `gh-<n>` nor a directory with `.10x/<id>/ticket.md`.

## 10x-security

`10x-security add <id> <file> | set <id> <fingerprint> <status> [reason] | remove <id> <fingerprint> | prepare | import run-<n> | ticket <fingerprint> <slug> | list --plannable | route <fingerprint>` — the one writer of `.10x/security.md`, the repo-wide record of what `10x:security-reviewer` found outside a ticket's diff, or could not confirm. The file lives under `.10x/`, so it is never committed. Refusals print `10x-security: <why>` with exit 2 and write nothing.

- `add` reads a JSON array of the reviewer's `## Out of diff` records from a file under `.10x/<id>/`. Each record has exactly `verdict` (`confirmed` or `needs_validation`), `rule` (kebab-case), `title`, `path` (repo-relative), `line` (an integer ≥ 1), `snippet`, `trace`, and `severity` (`critical`, `high`, `medium`, `low` or `informational`) only when confirmed; a fault prints `records[<i>]: <field> …` for each faulty record. A new fingerprint is appended with `status: new` and `found in: <id>` (`added: <fp>`); a known one gets `<id>` in `seen in` and nothing else changes (`seen: <fp>`).
- `set` records `fix-now`, `later`, `accepted` or `rejected` (the last two need a reason) and changes only `status` and `reason`. `remove` deletes one entry. Both refuse an unknown fingerprint and an entry whose `found in` and `seen in` do not include `<id>`, unless `.10x/<id>/ticket.md` (a regular file, not a symlink) has the header line `Security: <fingerprint>` — the ticket `10x-land advisory` or `ticket` made for it; `<id>` is a ticket id or an audit run id (`audit/run-<n>`, which `/10x:audit` passes). The grant hook binds all three to the session's ticket. `/10x:work` grants only `add`, and the hook never allows `set`, `remove` or `ticket`, so they always ask: any session can put its ticket into an entry's `seen in`.
- `10x-security prepare` (no arguments) looks for the `security-audit` skill in `<main checkout>/.claude/skills/` and then `~/.claude/skills/`. Without it, it prints the two `npx skills add` commands (project and `--global`) and exits 1, writing nothing. Otherwise it takes N as one more than the highest existing run; when git does not ignore `.10x/audit/run-<N>` it says so and exits 1 without creating it, else it creates the directory and prints `skill: <path>`, `run: <path>` and one `prior: <path>` per earlier run.
- `10x-security import run-<n>` merges `.10x/audit/run-<n>` into `security.md`. It reads `findings.json`, `run-metadata.json` and `rules.json`, and checks every record before it writes: any fault refuses the whole run, naming the record as `findings[<i>]`. `rules.json` is written by `/10x:audit` and maps each finding's `fingerprint` to a kebab-case rule, because the audit's records carry none. For each `confirmed` or `needs_validation` record the sink is the last `sink` entry of its `trace` and must exist in the checkout; the 10x fingerprint comes from the rule, the sink path and the sink line. A record matches an entry by `audit fingerprint`, then by 10x fingerprint: a match adds `audit/run-<n>` to `seen in` and refreshes `verdict`, `severity`, `location` and `trace`, keeping `title`, `status` and `reason`; otherwise a `new` entry is appended. `rejected` records are skipped. When `scope_paths` is exactly `["."]`, an entry not seen gets `audit/run-<n>` in `not seen in` and keeps its status. It prints `added: <fp>`, `seen: <fp> <status>`, `not seen: <fp>`, then `run_status: <value>`. Importing a run twice changes nothing.
- `10x-security ticket <fingerprint> <slug>` writes `.10x/<slug>/ticket.md` for an entry, in both `tickets` modes and without any `gh` call, and adds `<slug>` to the entry's `seen in`. The ticket names the entry only by its fingerprint. It refuses an unknown fingerprint, an existing `.10x/<slug>/`, and the slugs `gh-<n>`, `drafts` and `audit`.
- `10x-security list --plannable` prints `<fingerprint> <severity> later <title>` for each `confirmed` entry with status `later` whose fingerprint `.10x/roadmap.md` does not name, in file order; `/10x:roadmap` offers them as requirements. It writes nothing.
- `10x-security route <fingerprint>` prints how a ticket for the entry may be opened without disclosing it, `route: <route> — <reason>`, and writes nothing:

  | Case | Route |
  |---|---|
  | `tickets: files` | `ticket` (no `gh` call) |
  | origin's repo is `PRIVATE` or `INTERNAL` | `issue` |
  | `PUBLIC`, entry `needs_validation`, `low` or `informational` | `issue` |
  | `PUBLIC`, no tag | `issue` |
  | `PUBLIC`, the location line's commit (blamed at HEAD, following moves and copies) is in no tag | `issue` (unreleased) |
  | `PUBLIC`, a `confirmed` `medium`, `high` or `critical` entry released in a tag | `advisory` |

  It exits 2 on an unknown fingerprint, a location line that no longer exists at HEAD, no origin or a non-github.com origin, and a visibility `gh` cannot read: never a default route.
- With `TENX_BATCH` set (every batch worker has it), `set`, `remove` and `ticket` print `10x-security: refused inside a batch worker` and exit 2 before checking their arguments or reading anything; the other subcommands run as without it.
- Writes go through a temp file and a rename under the lock `.10x/security.lock`, and `.10x/` is kept in `.git/info/exclude`.

The fingerprint is `sha256:` and the hex sha256 of `<rule>\n<path>\n<snippet>`, where `snippet` is the sink line with each run of whitespace collapsed to one space and the ends trimmed. It has no line number, so the same sink keeps its fingerprint when the code around it moves, and it matches the fingerprint pattern of Cloudflare's security-audit-skill.

`.10x/security.md` is `# Security entries`, then one section per entry, separated by blank lines:

```markdown
## sha256:<hex>
- title: <text>
- verdict: confirmed
- severity: high
- rule: command-injection
- location: <path>:<line>
- trace: <text>
- status: new
- reason:
- found in: gh-1
- seen in: gh-4, gh-9
- audit fingerprint:
- not seen in:
```

Fields come in that order, one line each; an empty one ends at the colon. A backslash, newline, carriage return or tab in a value is stored as `\\`, `\n`, `\r`, `\t`. `audit fingerprint` and `not seen in` are written only by `import`; every other subcommand keeps them as they are. `seen in` and `found in` hold ticket ids or audit run ids (`audit/run-<n>`), `not seen in` audit run ids only. A file that does not parse makes every reader exit 2 with `<file>:<line>: <why>`.

## 10x-grill

`10x-grill` prints the shared grill (`references/grill.md`) that `/10x:open`, `/10x:work` and `/10x:roadmap` follow; a skill cannot Read a file under the plugin root without a prompt.

## 10x-ticket

- `10x-ticket github <ref> [--out <path>]` prints a GitHub issue of origin's repo as Markdown, or writes it to `--out`, which must be that issue's `.10x/gh-<n>/ticket.md` (a number, or that repo's issue URL; another repo's is refused, and so is any other argument). Inside a `/10x:batch` worker (`TENX_BATCH` set), `--out` exits 2 before any `gh` call when that ticket's `plan.md` has `Status: approved`, pointing the worker to Step 2 (`10x-worktree add gh-<n>`); `10x-batch init`, which runs without `TENX_BATCH`, still refreshes an approved ticket. When the issue body's first non-blank line, trailing whitespace and `\r` dropped, is exactly `Size: small`, it adds `- size: small` as the last line of the header it writes; the body stays verbatim, and the line anywhere else — lower in the body, in a comment — adds nothing.
- `10x-ticket issue-types` prints the issue types of origin's repo, one per line; nothing for a repo without them.
